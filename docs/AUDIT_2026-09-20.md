# GymBroFitness — cercetare comparativă și audit

Data: 20 septembrie 2026. Audit fără modificări funcționale. Evaluarea designului a folosit două evaluări independente: `/root/design_review` (UX/cod) și `/root/design_evidence` (detector, contrast, preview).

## Stadiu și verificări

Proiectul este un prototip avansat local-first, cu domeniu bine dezvoltat, dar cu integrare incompletă și probleme care împiedică lansarea responsabilă către utilizatori reali. Aceasta este o apreciere inginerească, nu o măsurare procentuală a finalizării.

- Expo 57, React Native 0.86, React 19, TypeScript, Expo Router, React Native Paper.
- SQLite/Drizzle pentru sesiuni și template-uri; AsyncStorage pentru profil și program.
- 179 fișiere TS/TSX, 87 definiții în catalogul programabil, 847 intrări în biblioteca de referință; acestea sunt două seturi diferite, nu 934 exerciții unice garantate.
- Onboarding local, generator și editor de programe, workout logger, autosalvare/restaurare, pauză, supersets, RIR, istoric, recorduri, analytics, body map și pipeline cameră MoveNet sunt implementate în cod.
- Autentificarea reală, sincronizarea, import/export pentru utilizator și distribuția verificată nu sunt demonstrate de implementarea inspectată.
- `npm run typecheck`: PASS; `npm run lint`: PASS; `npm test -- --runInBand`: 45 suite / 268 teste PASS.
- Preview web existent: eroare `Unable to resolve module ./wa-sqlite/wa-sqlite.wasm` în `expo-sqlite/web/worker.ts:22`. Nu s-a verificat UI funcțională, nici comportamentul pe dispozitive iOS/Android.
- Detector Impeccable pe `src/app`: zero rezultate; nu validează accesibilitatea React Native. Contrastul și țintele tactile au fost analizate separat.
- README și PRODUCT.md sunt parțial în urmă: onboardingul și editarea programelor există deja în cod.

## Aplicații comparate

| Referință | Ce oferă relevant | Ce merită preluat ca principiu |
|---|---|---|
| [Hevy](https://www.hevyapp.com/) | Logging, rutine, istoric, recorduri, grafice, comunitate, ceas și web | Viteza setului și continuitatea între sesiuni; funcțiile sociale pot aștepta |
| [Strong](https://www.strong.app/) | Logger, supersets, RPE, timer, calculator discuri, export CSV și integrări | Instrumente disponibile contextual, date portabile și acces rapid la precedent |
| [Fitbod](https://fitbod.me/) | Personalizare după obiective, nivel, echipament și istoricul antrenamentelor | Conectarea preferințelor și feedbackului la recomandări, cu explicații clare |
| [RP Hypertrophy](https://rpstrength.com/pages/hypertrophy-app) | Mesocicluri, progresie, ajustare după pump/soreness/workload | Buclă completă feedback → decizie → sesiune următoare; indicatorii noștri demo trebuie înlocuiți |
| [Boostcamp](https://www.boostcamp.app/) | Bibliotecă de programe, logare ghidată, progresie și instrumente de workout | Alegerea unui program după timp/nivel/echipament și explicarea logicii sale |

Acestea sunt capabilități documentate pe paginile produselor, nu rezultate ale unor teste comparative hands-on. Recomandările pentru GymBroFitness sunt concluziile auditului.

## Repository-uri comparate

1. [LiftLog](https://github.com/LiamMorrow/LiftLog) este cea mai apropiată referință tehnică: Expo, React Native, Paper, Router, date locale. Am inspectat [schema SQLite](https://github.com/LiamMorrow/LiftLog/blob/main/app/src/db/schema.ts) și [modelul timerului](https://github.com/LiamMorrow/LiftLog/blob/main/app/src/models/session-models/rest-timer.ts). Schema are payload-uri versionate și un invariant pentru sesiunea activă; timerul modelează explicit pornirea/pauza. Structura include backup, import, export și migrații. Merită studiată separarea modelului persistent de UI; adoptarea Redux sau a backendului său nu este necesară.
2. [Liftosaur](https://github.com/astashov/liftosaur) este referința pentru progresii declarative, deload și programe flexibile prin Liftoscript. Arborele actual conține implementări native și web, editoare de progresie, timere Android/iOS și backup. README-ul încă descrie PWA/wrappere: nu trebuie folosit singur pentru a deduce arhitectura curentă. Pentru noi sunt utile reguli explicite și testabile; un limbaj de scripting pentru utilizator ar fi prematur.
3. [Flexify](https://github.com/brandonp2412/Flexify) este Flutter, deci referință conceptuală, nu transplant de componente. Are logging offline, grafice, cardio, alarme și teme. Am inspectat [TimerService Android](https://github.com/brandonp2412/Flexify/blob/main/android/app/src/main/kotlin/com/presley/flexify/TimerService.kt): separă serviciul nativ, notificările și ciclul de viață. Arborele include scheme de migrare și teste de integrare.
4. [wger](https://github.com/wger-project/wger) este util pentru catalog, API, traduceri, administrarea datelor și self-hosting; nu este modelul direct pentru shell-ul mobil Expo. Licențele datelor sunt documentate separat de cod.
5. [Massive](https://github.com/brandonp2412/Massive) este un exemplu istoric React Native pentru logging offline, timer și grafice. README îl declară deprecated și trimite la Flexify; nu îl recomand ca bază nouă.

Licențe declarate în repository-uri: LiftLog/Liftosaur/wger AGPL-3.0, Massive GPL-3.0, Flexify MIT. Comparația de aici privește idei și arhitectură; reutilizarea codului trebuie evaluată separat.

## Lista 1 — tehnic

P0 = protecția datelor înainte de utilizare reală; P1 = funcționare corectă înainte de beta; P2 = consolidare; P3 = extindere.

1. **P0 — Eliminarea ștergerii automate a istoricului.** `src/domain/workouts/historyRepository.ts:7` fixează 100 sesiuni, iar `pruneOldSessions` șterge restul la salvare. Se pierd istoricul și baza recordurilor. Păstrare integrală, paginare/indexare și test de retenție peste 100 sesiuni; nu confunda limitarea afișării cu retenția datelor.
2. **P0 — Migrare fără pierdere de date.** `historyStore.ts:47` prinde inclusiv erorile de import SQLite, apoi șterge cheia veche în `finally`. Separă parse/validare/import, păstrează originalul până la confirmarea tranzacției, oferă retry și copie de recuperare. Test: eroare la al doilea insert, restart, apoi import fără pierderi sau duplicate.
3. **P0 — Finalizare și autosalvare coordonate.** `workout.tsx:437–464` marchează finalizarea inclusiv la eroare. Păstrează sesiunea recuperabilă până la commit, oprește/flushează autosave înainte de finish, serializează operațiile și adaugă retry idempotent. Separă eroarea de feedback haptic de eroarea de persistență. Testează finish în fereastra de debounce și eșecul DB.
4. **P1 — Unități conectate la UI.** `SetRow.tsx:196–198` este fixat pe kg; utilitarele `displayLoad` și `inputToKg` există, dar nu sunt folosite de formular. Stocare canonică kg, conversie doar la intrare/afișare, inclusiv sub-seturi, discuri, ținte și rezumate. Test: 135 lb se persistă în kg și revine corect la afișare.
5. **P1 — Input după tipul exercițiului.** SetRow afișează kg/reps indiferent de trackingType. Plank are `trackingType: time`, însă formularul nu oferă secunde. Introdu componente pentru greutate+repetări, bodyweight, greutate suplimentară și timp; validate numere finite, nenegative, repetări întregi și valori obligatorii înainte de bifare.
6. **P1 — Timer și durată corecte.** `RestTimer.tsx:53` scade câte o secundă prin interval; nu păstrează un termen absolut. Pauza workout schimbă statusul, fără actualizarea `totalPausedSeconds`. Persistă restEndsAt/pausedAt și recalculează la revenirea în foreground; notificare nativă pentru ecran blocat. Modelul LiftLog este un reper util.
7. **P1 — Date reale pentru readiness/mesociclu.** Home importă DEMO_PRE_WORKOUT_LOG și DEMO_MESOCYCLE_BLOCK. Introdu check-in și bloc persistent; propagă readiness/discomfort/volum săptămânal în motorul de progresie. Wrapperul `buildProgressionTarget` nu transmite readiness, iar apelurile UI inspectate nu furnizează toate semnalele disponibile în domeniu. Starea fără date trebuie să fie explicită.
8. **P1 — Identitate locală versus autentificare.** Onboarding validează parola, dar salvează doar profil/program local. Elimină parola din modul local sau implementează complet autentificarea. Dacă apare multi-user, izolează sesiuni/template-uri și migrează explicit datele guest: repository-ul curent de istoric nu filtrează după userId.
9. **P1 — Tranzacții și invariant unic al draftului.** Ștergerea drafturilor și inserarea celui nou sunt separate. Doi indici unici, unul pentru paused și unul pentru in_progress, permit în DB câte unul din fiecare. Folosește tranzacție și invariant comun pentru toate stările reluabile; protejează și salvarea profil+program de stări parțiale.
10. **P1 — Versiuni de schemă și validare la citire.** Bootstrap-ul CREATE IF NOT EXISTS nu este sistem de migrare. Payload-urile workout/template nu au envelope versionat; validarea legacy este superficială. Introdu schemaVersion, migrări incrementale, validare runtime și carantină pentru date invalide. JSON în SQLite rămâne o alegere acceptabilă.
11. **P1 — Suportul web și matricea platformelor.** Preview-ul este blocat de WASM. Metro adaugă tflite, nu configurarea web SQLite cerută. Urmează [documentația Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/) pentru WASM și headere; izolează camera prin implementări native/web. Validează web, development build Android și iOS separat; un test unit nu confirmă buildul.
12. **P1 — Integrare și CI.** Cele 268 teste trec, dar sunt concentrate în domeniu/repository. Adaugă teste pentru create → log → background → restore → finish → history, input lb/secunde, eroare DB, migrare, import și reset. Automatizează typecheck/lint/test și build smoke într-un pipeline. Nu este nevoie de teste care doar copiază implementarea.
13. **P2 — Cazurile limită ale progresiei.** În engine.ts:128–129 plafonul 30 se aplică și țintelor în secunde, deși ramura time încearcă să permită mai mult (:231). Separă constrângerile pe unități. Verifică și ordinea plafonării creșterii și rotunjirii la discuri, pentru a nu recomanda încărcări imposibile. Confirmare prin scenarii executabile înainte de schimbarea regulilor.
14. **P2 — Stare partajată, erori și separare a ecranelor.** workout.tsx are 1.762 linii, program.tsx 1.224; mai multe hookuri recitesc profilul/istoricul și unele promisiuni au finally fără catch. Extrage controllerul sesiunii, selecția țintelor și persistența; o sursă observabilă pentru profil/program/history, plus stări error/retry. Nu e necesară rescrierea domeniului.
15. **P2 — Portabilitatea datelor.** Backup JSON versionat, export CSV și import cu preview, maparea exercițiilor și deduplicare. O sesiune Hevy/Strong importată trebuie să intre în același istoric și aceleași analytics. Cloud sync poate urma după stabilizarea sursei locale, cu operații idempotente și rezolvarea conflictelor.
16. **P2 — Identitate unificată a exercițiilor.** Catalogul de 87 și atlasul de 847 au scopuri și ID-uri diferite. Introdu mapări explicite, aliasuri și o cale controlată de transformare în exercițiu logabil. Căutarea, istoricul, substituțiile și progresia trebuie să folosească aceeași identitate canonică.
17. **P2 — Validarea și performanța Form AI.** Configurarea pe movementPattern aplică pushUpConfig tuturor horizontal_push; eligibilitatea trebuie controlată pe exercițiu/variantă și unghi. Fiecare cadru ajunge în JS și setState: măsoară FPS, latență și consum, apoi limitează actualizările. Leagă isActive de focus/AppState, oprește speech la ieșire și oferă fallback la cameră/model indisponibil. Testele geometrice nu validează acuratețea pe video real.
18. **P2 — Documentație și dependențe.** Actualizează README/PRODUCT după cod; documentează native development build și limitările web. Verifică dependențele instalate fără consumatori în src, precum Supabase/Query/Zustand/RHF/Zod, înainte de păstrare sau eliminare. Definește config de release și identificatori finali. P3: integrări ceas/Health și sharing după stabilizarea fluxului principal.

## Lista 2 — design și UX

1. **P1 — Home orientat către următoarea acțiune.** Păstrează sus sesiunea de azi/reluarea, ținta principală și CTA. Mută blocurile secundare de recovery/PR/mesociclu în detalii. Astăzi Home are nouă blocuri după antet; greutatea informațională nu corespunde folosirii între seturi.
2. **P1 — Navigare grupată.** Șase taburi vizibile ocupă aceeași bară, în timp ce workout este ascuns. Propunere de testat: Azi, Plan, Progres, Exerciții; profil în avatar și Body în Progres. Adaugă o bară persistentă de reluare a sesiunii. Păstrează accesul la toate funcțiile existente.
3. **P1 — Logger compact.** Rândul principal: set, precedent, țintă, greutate, reps/secunde și bifă. Tehnici/drop set/superset în meniu contextual. Ținta și precedentul sunt acum microtext de 11 px. Crește informația critică, aliniaza cifrele și păstrează următorul set accesibil când tastatura este deschisă.
4. **P1 — Stări de salvare fără contradicții.** Sumarul spune Session saved chiar pe ramura de eroare. Definește Saving / Saved / Save failed cu retry și draft păstrat. Celebrarea recordurilor vine după confirmarea persistării. Momentul final trebuie să asigure utilizatorul că munca lui rămâne disponibilă.
5. **P1 — Onboarding local scurt.** Înlocuiește Account/parolă cu profil local și setările strict necesare. Arată planul devreme, mută preferințele avansate ulterior, cere cont doar când există beneficiu real și autentificare. Numele și copy-ul trebuie să reflecte exact ce se salvează.
6. **P1 — Date reale, estimări și lipsă de date distincte.** Elimină scorul Ready fabricat din formula limitată la 68–96 și textul green light permanent din HomePreflightRail. Folosește Nu ai făcut check-in / Estimare din ultimele sesiuni / Date insuficiente. Explicația indicatorului trebuie accesibilă la atingere.
7. **P1 — Contrast și text critic.** Contrast calculat textMuted dark pe surface: 3,87:1; light pe alb: 2,97:1. Pentru textul mic folosit în produs crește contrastul și evită microtextul pentru ținte/erori. Tema light este momentan forțată off, dar tokenurile trebuie corectate înaintea activării.
8. **P1 — Accesibilitate tactilă și semantică.** Heatmap are Pressable de 12×12 fără label/role. Oferă detalii accesibile prin ținte mai mari, selector de zi sau listă alternativă. Etichete pentru iconuri, stări checked/selected, semnal textual al culorilor și verificare TalkBack/VoiceOver/Dynamic Type.
9. **P2 — Charts și Body explicabile.** Graficele trebuie să spună perioadă, unitate, diferență față de precedent și număr de sesiuni. Separă volum, e1RM și număr de seturi. Body are nevoie de legendă și acțiune contextuală; culorile nu trebuie interpretate ca măsurare directă a recuperării. Zero și lipsa datelor sunt stări diferite.
10. **P2 — Responsive verificat.** analytics.tsx fixează două grafice la width=300; tab bar are bottom=24 și height=68; RIR sheet are înălțime procentuală și conținut fix. Măsoară containerul și safe areas, verifică 320/360/390/430 px, text mărit și tastatură. Overflow-ul nu a fost confirmat vizual în acest audit.
11. **P2 — Atlas conectat la acțiune.** Căutare, filtre echipament/mușchi, favorite/recente; pagina exercițiului să arate instrucțiuni, istoric și Adaugă/Înlocuiește. Fă vizibil dacă exercițiul este doar referință sau disponibil pentru plan. UI trebuie susținută de maparea ID-urilor din lista tehnică.
12. **P2 — Program library comparabilă.** Carduri cu zile/săptămână, timp/sesiune, nivel, echipament și accent muscular. Preview înainte de activare și explicația schimbărilor asupra planului actual; redenumirea, reordonarea și substituțiile rămân ușor de găsit.
13. **P2 — Limbaj și consistență.** Păstrează direcția negru/albastru, documentează DESIGN.md și standardizează spacing/titluri/butoane/stări. Explică RIR, e1RM, deload la nevoie. Hamburgerul Home deschide Settings: folosește iconul potrivit. Un limbaj coerent și formatarea locală sunt mai importante decât efecte noi.
14. **P2 — Form AI ghidat.** Setup cu unghi, distanță și încadrare; diferențiază Camera vede bine de Repetare corectă. Afișează un singur feedback prioritar și o acțiune de recalibrare. Model indisponibil, permisiune refuzată și exercițiu nesuportat trebuie să lase logarea manuală accesibilă.
15. **P2 — Motion și acțiuni destructive.** Reveal staggered și AnimatedNumber trebuie să respecte reduced motion și să nu întârzie datele critice. Confirmare cu efectele exacte la reset profil/plan și undo unde este practic. Personalitatea rămâne în progres și feedback, nu în animații repetitive.

## Evaluare euristică provizorie

Scor bazat pe cod, nu pe usability testing. Specificitatea vizuală este bună: harta musculară, RIR și țintele de progresie sunt relevante produsului. Puncte tari: autofill/copiere, autosalvare/restaurare și tokenuri semantice. Problema principală este încrederea în date și salvare.

| Euristică | Scor /4 |
|---|---:|
| Vizibilitatea stării | 2 |
| Potrivire cu lumea reală | 2 |
| Control și libertate | 2 |
| Consistență | 2 |
| Prevenirea erorilor | 1 |
| Recunoaștere în loc de memorare | 3 |
| Flexibilitate și eficiență | 3 |
| Minimalism | 2 |
| Recuperare după erori | 1 |
| Ajutor contextual | 2 |
| Total | 20/40 |

Începătorul este încărcat de onboarding și jargon; utilizatorul avansat beneficiază de autofill, dar are ținte mici și acțiuni dispersate; utilizatorul cu vedere redusă întâlnește contrast/ținte tactile insuficiente. Parcursul emoțional pierde încredere la finalizarea cu eroare, exact când ar trebui să ofere certitudine.

Ordine propusă: protecția datelor → logare/unități/timer → eliminarea demo-urilor și clarificarea profilului → simplificare Home/navigare → accesibilitate → backup/integrări → polish. Nu sunt necesare clarificări pentru livrarea auditului; implementarea poate fi planificată ulterior.

Note de execuție: evaluări A/B independente; target audit general src/app, fără snapshot de rută individuală; detector 0; fără overlay injectat; tabul temporar închis; niciun server pornit/oprit; procesul Expo preexistent păstrat. Doar acest raport a fost adăugat în proiect.
